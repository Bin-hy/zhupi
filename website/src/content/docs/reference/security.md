朱批是自托管服务，安全边界由「服务端配置 + 宿主页面 + 反向代理」共同决定。下面列出当前实现的实际防护与需要你负责的部分。

## 站点隔离

- 站点级请求必须带 `X-Site-Key` 与合法 `Origin`；两者都匹配才放行。
- `siteKey` 是**公开标识**，不是密钥。它只用于选择站点，访问控制靠 Origin 白名单。
- Origin 精确匹配 `scheme://host[:port]`，不做通配。
- 站点停用后立即拒绝站点级请求。
- 数据按 `site_id` 隔离，管理接口通过路径中的站点 ID 再次校验角色。

**你需要注意**：

- 不要把 `ALLOW_MISSING_ORIGIN=1` 用在生产；它允许非浏览器客户端绕过 Origin 校验。
- 新增预览域名、CDN 域名或自定义域名时，同步更新 Origin 白名单。
- 多站点场景不要在站点之间复用 siteKey。

## 密钥与凭据

| 数据 | 存储方式 |
| --- | --- |
| `SECRET_KEY` | 环境变量；32 字节 |
| OIDC client secret | AES-256-GCM 加密后入库 |
| 本地超管密码 | bcrypt 哈希 |
| 会话 token | 数据库只存 SHA-256 |
| OAuth state | 数据库只存哈希，带过期时间 |

**你需要注意**：

- `SECRET_KEY` 泄露等同于 OIDC client secret 泄露；更换密钥会导致已有 OIDC secret 无法解密。
- 备份数据库时必须同时妥善保管 `SECRET_KEY`。
- 不要把密钥写入镜像、仓库、前端变量或日志。
- 本地超管默认 `admin/admin` 只用于首次启动；生产必须改密，或只依赖 GitHub/OIDC。

## 客户端令牌与 XSS

SDK 把 Bearer token 存在宿主页面的 `localStorage` 中：

- 不使用 Cookie，因此没有传统 CSRF 问题；
- 但宿主页面一旦存在 XSS，攻击者可以读取 token 并冒用会话。

**你需要注意**：

- 保持宿主站点的 XSS 防护（CSP、可信依赖、输入转义）。
- 不要把 SDK 接入到允许用户注入任意脚本的页面。
- 对高敏感场景，考虑缩短 `SESSION_TTL_HOURS` 或退出所有设备。

批注/评论渲染会先转义全部 HTML，再放行行内代码、粗体、斜体、删除线、链接、换行；用户输入不会执行标签或脚本。

## 登录与授权

- GitHub OAuth 使用 state；OIDC 使用 state + PKCE + nonce。
- 回调地址由 `PUBLIC_BASE_URL` 拼接，生产必须是 HTTPS 外部地址。
- 全局封禁会拒绝登录与会话认证；站点封禁只拦截该站点写操作。
- 站点管理员不能修改站点设置（Origin、审核模式、状态），避免自行扩大访问面。
- 本地登录按 IP 限流。

## 限流与滥用

| 层 | 默认 |
| --- | --- |
| 读 | 300 / IP / 分钟 |
| 写 | 60 / IP / 分钟 |
| 写 | 30 / 用户 / 分钟 |
| 本地登录 | 10 / IP / 分钟 |

限流是进程内计数，重启清零，适合单实例的基础防滥用，不替代 WAF 或 CDN 防护。

## 反向代理

- 只把服务发布到 `127.0.0.1:8080`，由 Caddy/Nginx 提供 HTTPS。
- 只有存在可信代理时才设 `TRUST_PROXY=1`，并确保代理覆盖 `X-Forwarded-For`。
- 限制请求体大小（服务端硬限制 128 KiB）。
- 不要把管理后台直接暴露在无认证的公网路径之外——它本身有登录，但减少攻击面总是更好。

## 运维

- 定期备份数据库与 `SECRET_KEY`，并做恢复演练。
- 关注登录设备与异常 IP；必要时“退出所有设备”。
- 轮换 siteKey 时同步更新所有前端。
- 升级前阅读迁移变更；降级未必兼容新 schema。
- 当前没有审计日志、2FA、邮件通知与自动反垃圾；需要这些能力时应在反向代理/周边系统补足。
